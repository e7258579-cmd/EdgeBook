# EdgeBook — חוזה ה-Webhook (V01)

**מטרה:** להגדיר בדיוק מה ה-Pine שולח ל-Firebase Function, ומה ה-Function מחזירה ועושה. מסמך תכנון, עדיין לא ממומש בקוד.
**סימונים:** ✅ הוחלט · ⚠️ הנחה שלא אומתה · ❓ החלטה פתוחה

## 1. עקרונות

- ✅ ה-Pine **מדווח** על אות; ה-Function **מחליטה** אם לבצע. כל שדה מחיר או כמות בהודעה הוא **רמז** בלבד.
- ✅ גודל הפוזיציה נקבע **בצד השרת** (תקרת מניות + 1% מההון). `qtyHint` לא נאמן עליו.
- ✅ **כל הודעה מטופלת פעם אחת.** מפתח ייחודי מחושב בצד השרת: `symbol|event|barTime`. הודעה שנייה עם אותו מפתח נרשמת כ-`duplicate` ולא מבצעת כלום.
- ✅ ה-Pine שולח **רק בסגירת נר** (האסטרטגיה רצה פעם אחת לנר, `calc_on_every_tick = false`).
- ✅ הסיסמה (`secret`) נמצאת בגוף ההודעה, כי TradingView לא מאפשר כותרות מותאמות.

## 2. מבנה ההודעה (JSON)

שדות משותפים לכל הודעה:

| שדה | סוג | תיאור |
|---|---|---|
| `secret` | string | הסיסמה המשותפת |
| `v` | number | גרסת החוזה (`1`) |
| `event` | string | `"entry"` או `"exit"` |
| `symbol` | string | סמל המניה, אותיות גדולות |
| `barTime` | number | זמן **סגירת** הנר, ms מאז 1970 (`time_close`) |
| `tf` | string | מסגרת זמן בדקות, למשל `"1"` |
| `strategy` | string | גרסת האסטרטגיה, למשל `"V05"` |
| `session` | string | `"pre"` (פרה-מרקט) או `"regular"` |

שדות נוספים לכניסה (`event = "entry"`):

| שדה | סוג | תיאור |
|---|---|---|
| `price` | number | מחיר הכניסה המשוער (הטריגר, או הפתיחה אם היה Gap) |
| `stop` | number | שפל הנר האדום האחרון, רמת הסטופ |
| `trigger` | number | רמת הטריגר |
| `mode` | string | `"stopbuy"` או `"close"` |
| `qtyHint` | number | הכמות באסטרטגיה (לא נאמן עליה) |

שדות נוספים ליציאה (`event = "exit"`):

| שדה | סוג | תיאור |
|---|---|---|
| `reason` | string | סיבת היציאה: `peak_trail`, `climax_exit`, `stall_detected`, `ema9_trail`, `ema20_trail`, `ema{N}_trail`, `pre_open_exit`, `stop_hit_premarket`, `stop_hit_regular_hours_backend_handles` |
| `price` | number | מחיר היציאה המשוער |

דוגמה, כניסה:

```json
{"secret":"***","v":1,"event":"entry","symbol":"WHLR","barTime":1759745340000,"tf":"1","strategy":"V05","session":"pre","price":4.06,"stop":3.78,"trigger":4.06,"mode":"stopbuy","qtyHint":25}
```

דוגמה, יציאה:

```json
{"secret":"***","v":1,"event":"exit","symbol":"WHLR","barTime":1759747740000,"tf":"1","strategy":"V05","session":"pre","reason":"peak_trail","price":3.76}
```

## 3. מה ה-Function עושה

**ארכיטקטורה מוצעת בשני שלבים** (❓ ממתין לאישור): TradingView ממתין לתגובה זמן קצר בלבד, ו-Cloud Functions עלולה לקטוע עבודה שנמשכת אחרי שליחת התשובה. לכן:

- **מקלט (Receiver):** Function שמקבלת את ההודעה, מאמתת, מונעת כפילויות ו**כותבת אות ל-Firestore** (`signals`), ועונה מיד (`queued`). אין בה קריאה ל-TradeZero.
- **מעבד (Processor):** Function שמופעלת מכתיבת האות (`onDocumentCreated`), מבצעת את כל שאר השלבים מול TradeZero, וכותבת את התוצאה על אותו מסמך. ההפעלה היא "לפחות פעם אחת", ולכן המעבד גם הוא אידמפוטנטי (בודק סטטוס המסמך לפני פעולה).

שלבים (כל אחד יכול לדחות; 1–2 במקלט, השאר במעבד):

1. **אימות:** `secret` תקין, `v` נתמך, כל השדות החובה קיימים ובטווח הגיוני. אחרת: `400` או `401`.
2. **מניעת כפילויות:** יצירת מסמך לפי המפתח בטרנזקציה. קיים כבר → `duplicate`.
3. **Kill Switch:** מסמך בקרה ב-Firestore. אם הוא פעיל → נדחה (`kill_switch`).
4. **מגבלות:** ✅ הפסד יומי מקסימלי **20$** (בשלב הדמו). מקסימום עסקאות ליום והזמנות לדקה: ערכים יוגדרו בקוד כברירת מחדל. חריגה → נדחה. הפסד יומי = סכום הפסדי העסקאות שנסגרו היום (מתוך הרישום שלנו ב-Firestore); כשמגיע ל-20$ ה-Kill Switch מופעל אוטומטית עד סוף היום.
5. כניסה בלבד: **אין כבר פוזיציה או הזמנה פתוחה בסמל** (בדיקה מול TradeZero). אחרת → נדחה (`already_in_position`).
6. כניסה בלבד: חישוב גודל פוזיציה (תקרת מניות, 1% מההון מול מרחק הסטופ), ושליחת פקודת **Limit במחיר + 0.10$** (✅ הוחלט, בכל שעות היום, אין פקודות Market). סטופ אמיתי בשעות הרגילות: עדיין לא ממומש.
7. יציאה בלבד: אם אין פוזיציה → `ignored` (נרשם). אחרת: ביטול הסטופ התלוי, ואז סגירה. פקודת Limit במחיר - 0.10$ (✅ הוחלט).
8. **רישום:** כל הודעה, החלטה וסיבה נרשמות ב-Firestore, גם הודעות שנדחו.

## 4. תשובה

המקלט מחזיר JSON עם סטטוס HTTP. התוצאה הסופית של העיבוד נכתבת ל-Firestore ולא חוזרת ב-HTTP.

| מצב | HTTP | גוף |
|---|---|---|
| התקבל ונכנס לתור | 200 | `{"ok":true,"status":"queued"}` |
| כפילות | 200 | `{"ok":true,"status":"duplicate"}` |
| הודעה פגומה | 400 | `{"ok":false,"error":"..."}` |
| סיסמה שגויה | 401 | `unauthorized` |

סטטוס סופי של אות (במסמך ב-Firestore): `accepted`, `rejected` (עם `reason`), `ignored`, `error`.

## 5. מצבי הפעלה

- ✅ **DRY_RUN** (ברירת מחדל): המעבד עושה את כל השלבים, אבל **לא** קורא ל-TradeZero ורק רושם מה הוא היה שולח.
- אחרי שהלוגים נראים תקינים: מעבר ל-**Paper**.

## 6. שאלות פתוחות

1. ✅ **זמן תגובה:** הפיצול למקלט ומעבד אושר (סעיף 3). המחיר: עיכוב נוסף של פחות משנייה בהפעלת המעבד, ו-cold start אפשרי.
2. ✅ **הגנה בפרה-מרקט (אושר שתיבנה אחרי הזרימה הראשית):** אין סטופ אמיתי אצל הברוקר בפרה-מרקט, ולכן החלטנו (STATE) על "Dead-man's switch" בסקר: Function מתוזמנת שבודקת תקופתית אם פוזיציה פתוחה ירדה מתחת לסטופ השמור, וסוגרת אותה. מוצע לבנות אותה **אחרי** שהזרימה הראשית עובדת. עד אז, ההגנה בפרה-מרקט היא רק ה-Pine והמגבלה היומית (20$).
3. ✅ **הפסד יומי מקסימלי:** 20$ (שלב הדמו, ישונה בהמשך).
4. ✅ **סוג הפקודות:** תמיד Limit (אין Market בפרה-מרקט). קנייה: `price + 0.10`, מכירה: `price - 0.10` (דולרים, ניתן לשינוי ב-`control/config`).

## 7. מימוש

מומש ב-`skeleton/functions/` (ראה `skeleton/README.md`): מקלט, מעבד, מניעת כפילויות, גודל פוזיציה, מגבלות, DRY_RUN, ו-20 בדיקות יחידה. חסר: `cancelOrder`, קריאת פוזיציות מ-TradeZero, מעקב מילויים, סטופ אמיתי, Dead-man's switch.
